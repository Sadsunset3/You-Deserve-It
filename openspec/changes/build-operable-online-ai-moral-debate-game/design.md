## Context

仓库当前只有《活该》的背景与规则文档，没有应用代码。MVP 的目的不是建立完整运营平台，而是快速验证两名好友在独立设备上通过人物、词条和限时辩论影响 AI 列车长的体验。已确认：在线双人房间码邀请；后端调用 OpenAI 兼容 API；无账号昵称会话及掉线重连；房主配置局数和计时；每局固定三回合，每人开局 3 好人、3 恶人、6 词条；内容来自内置牌库；桌面端公网 MVP。

## Goals / Non-Goals

**Goals:**

- 用最少运行组件交付完整、可恢复的在线双人比赛。
- 服务端权威执行规则、倒计时、随机发牌和 AI 裁决。
- AI 失败时不中断比赛，能够形成最终审判与哲学评议。
- 用原创荒诞黑白漫画视觉建立鲜明氛围，并保证辩词和状态可读。
- 单个 Docker 应用配合 SQLite 即可部署和备份。

**Non-Goals:**

- 管理端、玩家注册登录、用户管理、封禁、付费、额度和长期战绩。
- 玩家上传卡面、自定义牌库或在线编辑内容。
- 公开匹配、观战、聊天、语音和排行榜。
- AI 模型、用量或成本管理界面。
- Redis、PostgreSQL、对象存储、微服务和多实例横向扩展。
- 移动端完整适配；小屏只提供横屏/桌面提示。

## Decisions

### 1. React + Node.js TypeScript 单体

采用 pnpm workspace：`apps/web` 使用 React、TypeScript、Vite；`apps/server` 使用 Node.js、Fastify、Socket.IO；`packages/contracts` 共享 Zod Schema 与 TypeScript 类型。生产构建由 Fastify 同源托管前端静态文件与 API/Socket，避免跨域和多服务部署。

该方案比 Next.js + NestJS 更轻、更适合一次性房间 MVP；比纯前端方案更能安全保存 AI 密钥并保证实时状态权威。明确限制为单实例，不提前引入 Redis 或分布式锁。

### 2. 内存权威状态 + SQLite 恢复快照

活跃房间在单个 Node.js 进程内存中运行，以保证状态机转换简单且低延迟。每次关键转换通过 Drizzle ORM 事务写入 SQLite 快照；进程重启时恢复未过期房间并根据绝对截止时间补推进超时阶段。比赛结束 24 小时后后台任务清理房间、辩词和会话关联。

SQLite 开启 WAL 和 busy timeout；写操作统一经过房间串行命令队列。若未来需要多实例，再将房间执行器和状态迁移到 Redis/PostgreSQL，不属于 MVP。

### 3. 服务端权威状态机

状态依次为 `WAITING → DEALING → CHARACTER_SELECTION → TRAIT_PLACEMENT → ATTACK_A → DEFENSE_B → VERDICT_A → ATTACK_B → DEFENSE_A → VERDICT_B → ROUND_END`；三回合后进入 `FINAL_JUDGMENT → PHILOSOPHICAL_REVIEW → GAME_END`，按配置局数重复后进入 `MATCH_END`。

客户端只发送带 `commandId` 和 `expectedVersion` 的意图。服务端校验席位、阶段、卡牌所有权和截止时间；重复命令幂等返回，旧版本命令被拒绝。计时基于服务端 UTC 截止时间，客户端倒计时只作展示。

### 4. 自定义规则有安全范围

房主可配置比赛局数 1–5、选牌 20–120 秒、词条 20–180 秒、攻击与防守各 30–180 秒、掉线判负 60–300 秒。每局仍固定三回合。选牌超时由服务端按稳定排序补足；词条超时直接结束；攻击或防守超时记空提交并判当前发言方输掉本次攻防；掉线超时判负整场比赛。

### 5. 轻量会话与重连

首次访问由后端签发不可预测的 `playerId` 和 HttpOnly 会话 Cookie。加入房间后再签发绑定玩家、房间和席位的短期重连令牌。昵称限制 2–20 字符。无注册、密码、管理员和封禁系统。

### 6. 内置版本化牌库

人物、词条、列车长人格和默认卡面作为只读资源随应用发布。人物必须包含 `good`/`evil` 分类、背景和本地卡面路径；人格必须包含可执行的价值判断规则。启动时 Zod 校验唯一 ID、字段、资源存在性及最低数量。

每局为每人独立随机发放 3 好人、3 恶人和 6 词条，并选择一个人格。使用加密安全随机源；为测试和 AI 降级记录服务器种子。玩家没有任何上传入口或 API。

### 7. AI 网关与降级

服务端从环境变量读取兼容 API 地址、密钥和模型，内部仅暴露 `adjudicateDebate`、`judgeGame`、`reviewPhilosophy` 三个用例。输出通过 JSON Schema/Zod 验证。请求超时后最多重试两次；仍失败则基于人格权重、人物分类、词条预置极性和有效辩词长度执行带种子的确定性降级，并标记 `fallback=true`。

MVP 只保留故障排查需要的请求 ID、用途、延迟和状态，不建立用量、成本、配额或管理能力。日志不得记录密钥、Cookie、重连令牌或完整辩词。

### 8. 原创荒诞漫画视觉

视觉方向借鉴网络荒诞漫画的共性语言：黑白粗线、夸张表情、低保真剪贴、网点纹理、撕纸边缘与有限警示红。不得复制“暴走漫画”的角色脸、标识、具体素材、专有字体或经典构图。默认卡面采用原创占位插画/剪影和身份符号。

设计以 1440×900 为基准、1280×720 为最低验收尺寸。攻防文本区优先可读性；关键状态不只靠颜色；动画尊重 `prefers-reduced-motion`；小屏显示横屏或桌面提示。

### 9. 安全、部署与测试

Fastify 和 Socket.IO 校验 Origin、会话、输入长度和阶段权限；昵称 2–20 字符，辩词最大 2,000 Unicode 字符；房间创建、加入和发言有限流。Docker 多阶段构建生成一个应用镜像，挂载 SQLite 数据卷，通过反向代理/TLS 公网部署。

测试包括：Vitest 的规则/状态机/降级单测，Fastify 注入与 Socket.IO 集成测试，Playwright 双浏览器完整比赛、断线重连、超时和刷新恢复测试。

## Risks / Trade-offs

- [单实例无法横向扩展] → MVP 明确单实例部署并记录未来状态存储迁移边界。
- [SQLite 写竞争] → WAL、串行房间命令、短事务和压力测试；不把高频倒计时逐秒写库。
- [AI 延迟或非法输出] → 超时、两次重试、结构校验和确定性降级。
- [重启时状态不一致] → 关键阶段快照、绝对截止时间和恢复集成测试。
- [视觉侵权或过度模仿] → 只提取通用风格特征，所有人物、卡面、字体和素材保持原创或明确许可。
- [内置内容更新需重新发布] → 接受该 MVP 取舍；管理端待验证核心玩法后另立 OpenSpec 变更。

## Migration Plan

1. 建立 workspace、共享契约、质量门禁和单体运行骨架。
2. 创建 SQLite Schema、内置牌库和默认卡面，完成启动校验。
3. 依次实现规则引擎、实时房间、AI 网关、React 流程和原创视觉。
4. 通过双浏览器端到端、重启恢复和 AI 降级演练后构建 Docker 镜像。
5. 回滚时停止新房间、替换为上一镜像并保留 SQLite 卷；数据库迁移保持向后兼容。
