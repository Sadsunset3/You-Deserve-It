# 《活该》实时攻防聊天室与时间规则重构设计

## 目标

把现有“攻方单条提交、守方单条提交、弹窗裁决”的攻防流程替换为服务端权威的双人实时聊天室。每轮由攻方先锁定对方轨道上的目标人物，再开启可配置为 3–10 分钟整数分钟的自由聊天。倒计时结束后，AI 列车长根据自身人设、目标人物完整档案和双方全部聊天裁决胜负，并以列车长头像在消息流中发送口语化裁决。

同时调整房间时间与掉线规则：限时模式下选人和词条默认时间均扩展为当前默认值的三倍，即各 180 秒；房主也可选择不限时，此时只有选人和词条不设截止时间，攻防聊天室始终按房主选择的分钟数倒计时。移除掉线判负秒数，比赛开始后任一玩家断线立即判对方整场获胜，原房不恢复。

## 已确认规则

- 首页创建房间增加“限时 / 不限时”选择。
- 限时模式默认选人 180 秒、词条 180 秒；两项仍可配置。
- 不限时模式只影响选人和词条阶段。
- 攻防聊天室时长由房主选择，范围为 3–10 的整数分钟，默认 5 分钟；不限时房间也必须使用该倒计时。
- 每轮攻方先选择并锁定对方轨道上的一名目标人物，锁定前不启动聊天室倒计时。
- 目标锁定后，双方可在倒计时内自由实时聊天，消息总条数不限，单条最多 2000 字。
- 聊天发言是甲乙两名真实玩家替躺在轨道上的自己及自己所在阵营辩护，不是目标人物以第一人称发言。目标人物是本轮被攻防讨论的对象。
- 倒计时结束后立即禁止新消息，并自动调用列车长裁决。
- 每轮裁决必须生成：胜方、符合列车长人设的口语化裁决消息、双方全轮交锋摘要、仅含胜方观点的简短辩词摘要。
- 全轮交锋摘要保存到轮次记录，供三轮后的最终压轨与最终审判使用。
- 胜方辩词摘要附加到本轮目标人物，后续轮次、最终压轨和最终审判均可读取。
- 裁决仍在聊天室消息流中展示，由列车长头像发送一条消息；展示后服务端自动进入下一轮，第三轮后进入最终压轨。
- 所有房间内页面持续显示双方在线状态；尚未创建或加入房间的首页不显示对手状态。
- 候场阶段断线只更新在线状态，不判胜负。
- 比赛开始后，玩家最后一个房间 Socket 连接断开即结束整场，对方直接获胜；掉线者只能回首页重新创建或加入新房，不能恢复原局。

## 方案选择

采用服务端权威聊天室。聊天记录、倒计时、封口、AI 裁决和阶段推进都由 `RoomManager` 控制，Socket.IO 只负责向两个玩家实时广播服务端状态和新增消息。该方案沿用现有服务端权威架构，支持刷新恢复、同时发言、幂等写入和可靠超时推进。

不采用独立聊天服务，因为当前聊天室仅存在于双人短时攻防轮次，拆出单独服务会增加不必要的部署和一致性成本。不在旧 `attack-input` / `defense-input` 上叠加消息数组，因为其轮流单次提交语义与双方自由发言冲突。

## 状态机

```text
waiting
  -> selecting
  -> traits
  -> target-selecting
  -> debate-chat
  -> round-adjudicating
  -> round-result
     -> target-selecting       （第 1、2 轮，攻守互换）
     -> track-adjudicating     （第 3 轮）
  -> judgment-generating
  -> judgment
  -> between-games / match-end
```

### `target-selecting`

只有本轮攻方可以从对方轨道的三名人物中选择目标。服务端验证目标确实位于守方轨道且尚处于当前局公开人物集合。锁定目标后才创建聊天室截止时间并进入 `debate-chat`。

### `debate-chat`

双方均可发送消息，不再限制发言顺序或每人消息数。服务器校验玩家身份、当前阶段、截止时间、非空文本和 2000 字上限，并为消息分配单调递增的 `sequence`。客户端按 `sequence` 排序，不能以本地到达顺序代替服务端顺序。

### `round-adjudicating`

服务器在截止时间到达后原子地关闭消息入口，冻结一份有序消息快照，再调用 AI。任何到点后到达的消息都被拒绝。AI 调用期间先广播裁决中状态，避免页面看似冻结。

### `round-result`

服务端保存结构化裁决，并把列车长裁决作为特殊消息附加到只读消息流。客户端展示裁决消息后，由服务端短暂延时并自动推进；不再由某一方点击“下一轮”。第三轮结束后直接进入最终压轨。

## 公共契约与核心数据

```ts
type TimingMode = 'timed' | 'unlimited';

type GameConfig = {
  games: 1 | 3 | 5;
  timingMode: TimingMode;
  selectionSeconds: number;
  traitSeconds: number;
  debateMinutes: 3 | 4 | 5 | 6 | 7 | 8 | 9 | 10;
};

type DebateMessage = {
  messageId: string;
  sequence: number;
  sender: 'a' | 'b';
  text: string;
  sentAt: string;
};

type DebateRoundVerdict = {
  winnerSeat: 'a' | 'b';
  conductorMessage: string;
  debateSummary: string;
  winningSummary: string;
  fallback: boolean;
};

type DebateRoundRecord = {
  round: 1 | 2 | 3;
  attacker: 'a' | 'b';
  defender: 'a' | 'b';
  targetId: string;
  messages: DebateMessage[];
  verdict: DebateRoundVerdict;
};
```

`disconnectSeconds`、单条 `SpeechRecord`、`currentAttack`、`currentDefense`、旧攻击/防守提交 schema 与旧回合胜负结构全部移除。房间保存当前轮 `debateMessages` 和下一 `messageSequence`；完成裁决后将其整体转移到 `roundRecords`。

`selectionSeconds` 与 `traitSeconds` 在不限时模式下仍保留配置值，便于切回限时模式和兼容房间表单，但服务端进入对应阶段时将 `deadline` 设置为 `null`。聊天室截止时间始终按 `debateMinutes * 60` 计算。

## 实时消息协议

普通房间命令继续使用 `commandId + expectedVersion`。聊天追加不使用房间 `expectedVersion`，否则双方同时发言会互相制造版本冲突。

发送消息请求只包含：

```ts
{ messageId: string; text: string }
```

`messageId` 用于幂等；同一玩家重复发送相同 ID 时返回已有消息，不重复写入。服务端在单个原子操作中验证阶段、分配序号、保存消息并广播。房间阶段变更和聊天室封口仍通过房间版本保护，保证裁决只消费一次冻结快照。

消息数量不设业务上限。为避免单个请求滥用，单条文本保持 2000 字上限，并沿用服务器请求体大小与基础频率保护；频率保护不能限制整轮可发送的总条数。

## AI 裁决与 Prompt

每轮只进行一次结构化 AI 调用，同时完成裁决、全轮整理和胜方摘要，减少等待并避免多次调用结果不一致。输入必须包含：

- 列车长 ID、名称、人设、规则与偏好；
- 目标人物名称、背景、全部词条和历轮累计胜出辩词；
- 本轮攻方、守方、双方昵称；
- 按服务端序号排序的本轮全部聊天消息；
- 之前轮次的目标、胜负、`debateSummary` 与 `winningSummary`。

回合 system prompt 明确以下语义：

1. 发言者是两名躺在各自轨道上的真实玩家，他们代表自己和自己所在轨道辩护。
2. 目标人物是被讨论、被攻击或被维护的对象，不能把玩家消息误写成目标人物的自述。
3. `conductorMessage` 必须像当前列车长依照人设会亲口说出的自然话，先简短复述关键交锋，再明确宣布胜方并说明理由；避免报告式、法条式和通用 AI 腔。
4. `debateSummary` 必须同时覆盖双方的主要观点、直接交锋、分歧和决定胜负的节点，供三轮后的裁决使用。
5. `winningSummary` 只能从胜方本轮实际发送的消息提炼，不得混入败方观点或新增事实，并压缩为可附加到目标人物的一段简短辩词。

最终压轨输入包含全部人物档案、三轮完整记录、三份 `debateSummary`、三份 `winningSummary` 和列车长人设。最终审判输入再加入最终压轨决定和理由。两类 Prompt 同样明确玩家发言的代指关系，不能把聊天误归因于目标人物。

AI 超时、限流、Key 失效、非法 JSON 或结构校验失败时，使用确定性本地备用裁决。备用结果也必须生成非空的口语化 `conductorMessage`、双方交锋 `debateSummary` 和胜方 `winningSummary`，房间不得停在裁决中。

## 前端页面

删除 `DebateModal` 及相关遮罩样式，新增独立全屏 `DebateChatPage`：

- 顶栏展示房间码、局数、轮次、攻守身份、双方在线状态和精确到秒的倒计时。
- 左侧为目标人物档案，展示人物名、背景、全部词条和累计胜出辩词；`target-selecting` 时为攻方展示三个候选目标。
- 右侧为列车长档案，展示头像、名称、人设和裁决规则。
- 中间消息流按服务端序号展示双方消息，显示昵称、阵营和发送时间，并自动跟随最新消息但允许用户回看。
- 底部为多行输入框和发送按钮，支持键盘发送与明确的组合键提示；到点、断线、裁决中或裁决完成后禁用。
- 裁决消息使用列车长头像和独立气泡样式，但仍位于同一消息流中。

在线状态提取为共享房间级组件，放入候场、选人、词条、目标选择、聊天室、裁决、审判和整场结束页面的固定可见区域。没有对手的首页不渲染虚构状态。

## 掉线处理

候场阶段允许玩家暂时离线，仅广播在线状态。比赛从 `selecting` 开始后，服务器确认某玩家不存在任何该房间的活动 Socket 连接时，立即：

1. 将对方设为整场胜者；
2. 清除所有阶段截止时间并关闭聊天写入；
3. 进入 `match-end` 并广播掉线判负理由；
4. 标记原房不可恢复，后续订阅不能把掉线玩家重新带回比赛。

页面刷新会断开 Socket，因此比赛中刷新也属于掉线并立即判负。这是已确认的严格规则，客户端应在开局前和房间内明确提示。

## 快照迁移

等待中的旧房间补齐 `timingMode: 'timed'`、`debateMinutes: 5`，删除字段只在读取时忽略。已进入旧 `attack-input`、`defense-input`、`round-adjudicating` 或 `round-result` 流程的房间不能无损映射到自由聊天，迁移后安全进入 `match-end`，提示版本升级后需要重新开局。已经结束的房间保持结束状态。

## 错误与并发边界

- 非房间成员、非当前阶段、目标未锁定、过期消息、空消息和超长消息均被拒绝。
- 攻方锁定目标仍使用版本化命令，重复命令不重复启动倒计时。
- 消息追加按 `messageId` 幂等，双方并发发送都能成功并获得唯一序号。
- 截止时间与消息写入在同一服务端临界区判断；服务器时间为唯一依据。
- AI 结果使用裁决开始时的版本或裁决令牌条件写回，迟到结果不能覆盖掉线结束或已推进房间。
- Socket 广播失败不回滚已持久化消息；客户端重连只适用于候场，候场重连后通过完整房间视图补齐状态。

## 测试与验收

### 契约与表单

- `debateMinutes` 只接受 3–10 的整数，默认 5 分钟。
- `disconnectSeconds` 不再出现在公共 schema、首页表单或错误文案中。
- 限时默认选人和词条均为 180 秒；不限时模式下对应阶段无截止时间。

### 服务端

- 目标锁定前聊天室不计时，锁定后准确设置配置分钟数的截止时间。
- 双方同时发送消息均成功，服务端序号唯一、递增且稳定。
- 重复 `messageId` 不产生重复消息；消息总条数不设上限；单条 2000 字上限生效。
- 截止时间到达后新消息被拒绝，只触发一次 AI 裁决。
- AI 输入包含完整列车长、目标人物、词条、累计辩词、全部有序聊天和历史轮次摘要。
- 每轮保存 `debateSummary`，三轮后的最终压轨和最终审判都收到三份摘要及相关原始记录。
- 只有 `winningSummary` 附加到目标人物，且类型与胜方的攻守身份一致。
- AI 失败时备用裁决字段齐全且状态机继续推进。
- 比赛中任一玩家最后一个连接断开后立即判对方整场获胜，原房不可恢复；候场断线不判胜负。

### 前端

- 所有房间内页面可见双方在线状态。
- 攻防使用独立聊天室页面，不存在旧攻防弹窗和旧单条提交控件。
- 目标档案、列车长档案、倒计时、历史消息和输入区完整展示。
- 双方消息实时出现且顺序一致，到点后输入立即禁用。
- 列车长裁决以头像消息出现，内容口语化并明确胜方与理由，随后自动进入下一轮。
- 刷新前有明确的“比赛中刷新视为掉线判负”提示。

### 全量验证

- 契约、服务端状态机、AI Prompt、Socket/HTTP 集成和前端组件测试通过。
- `pnpm test`、`pnpm typecheck`、`pnpm lint`、`pnpm build` 全部通过。
